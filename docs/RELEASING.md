# Releasing Recordish

This repository has two release channels:

- **Stable** releases are reviewed Semantic Version releases such as `v1.1.0`.
- **Nightly** is a rolling prerelease rebuilt from every successful `main`
  commit. It is useful for testing and is not promoted as the normal download.

The mod targets Minecraft 1.8.9, Forge 11.15.1.2318, and Java 8. Gradle requires
JDK 17 or newer as its host; CI compiles and verifies the mod with an explicitly
installed JDK 8 toolchain.

## Version source of truth

`version.txt` contains the current stable semantic version. Release Please owns
updates to that file, `CHANGELOG.md`, and
`.github/release/.release-please-manifest.json`. Minecraft, Forge, and Java
versions are release metadata rather than part of the semantic version.

The temporary `last-release-sha` in the Release Please configuration marks the
post-split history baseline. It prevents imported website and CI commits after
`v1.1.0` from becoming a mod release. Remove that key from the first legitimate
post-split release PR before merging it; the new release tag then becomes the
normal baseline.

The stable artifact name is:

```text
recordish-<version>-forge-1.8.9.jar
```

Do not edit checksums, manifests, or built JARs by hand. They are generated from
the exact release build.

## Conventional Commit rules

Release Please determines the next stable version from commits on `main`:

- `fix: ...` increments the patch version.
- `feat: ...` increments the minor version.
- `feat!: ...`, `fix!: ...`, or a `BREAKING CHANGE:` footer increments the
  major version.
- `docs:`, `test:`, `build:`, `ci:`, and `chore:` do not normally request a
  stable mod release.

Use squash merges and give the squash commit a clear Conventional Commit title.
Documentation-only commits are excluded from the mod release calculation.

## Stable release flow

1. Review the Release Please PR and wait for its normal CI checks.
2. Merge the Release Please PR.
3. `.github/workflows/release.yml` creates a version tag and draft GitHub
   Release, then checks out that exact tagged commit.
4. The workflow rebuilds and tests the mod, verifies the remapped JAR and Java 8
   bytecode, computes its SHA-256 fingerprint, and generates
   `release-manifest.json`.
5. The versioned JAR, checksum, and manifest are uploaded while the release is
   still a draft.
6. Only after every upload succeeds is the release published and marked latest.

A failed stable build leaves a recoverable draft instead of publishing an
unverified JAR. The stable download URL is immutable and versioned.

The website is maintained in a separate private repository. Its scheduled
release-sync workflow reads the latest public `release-manifest.json`, validates
and tests the static site, commits changed metadata, and lets Vercel deploy the
result to `recordish.kmsi.me`. Run that private workflow manually when an
immediate website refresh is required.

## Nightly flow

Every successful push to `main` builds from the stable base in `version.txt`:

```text
<base-version>-nightly.<run-number>.g<short-commit>
```

CI verifies that the commit is still the head of `main` before packaging and
again immediately before it updates the dedicated moving `nightly` tag. Its
public assets keep fixed names:

```text
recordish-nightly-forge-1.8.9.jar
recordish-nightly-forge-1.8.9.jar.sha256
nightly-manifest.json
```

The nightly release must remain a prerelease so GitHub's `latest` endpoint
continues to identify the latest stable build.

## Manual stable recovery

Run the **Release** workflow manually with the existing draft tag, such as
`v1.2.0`. The recovery path:

- refuses malformed tags;
- requires an existing draft release;
- checks out the exact tagged commit;
- rebuilds, verifies, and replaces the draft assets; and
- publishes only after every check succeeds.

It refuses to replace assets on an already-published stable release.

## Required repository settings

GitHub Actions must be allowed to:

- create and update pull requests for Release Please;
- write GitHub Releases; and
- update the dedicated `nightly` tag.

Release Please normally uses the repository's built-in `GITHUB_TOKEN`. GitHub
does not start pull-request workflows for PR activity generated by that token.
To run CI automatically on generated Release Please PRs, configure a
fine-grained personal access token or GitHub App token as
`RELEASE_PLEASE_TOKEN`. Give it only the repository contents, issues, and
pull-request access Release Please requires. The workflow falls back to
`GITHUB_TOKEN` when the secret is absent.

No personal token is required to build, verify, or publish the exact stable
artifact. Checkout credentials are not persisted; write tokens are exposed
only to the narrow release and tag steps. Never commit deployment credentials,
access tokens, or signing keys to this repository.

## Release checks and legacy caveats

- Publish only `build/libs/*.jar`, the final remapped artifact. Files under
  `build/intermediates` are not distributable.
- The released JAR must be the exact bytes that were hashed and tested.
- `pipelineSmokeTest` is manual because its missing-FFmpeg fallback check is not
  isolated from an FFmpeg executable already available on the runner.
- The FFmpeg installer smoke test performs a live external download. Keep it
  scheduled or manual rather than making releases depend on an upstream host.
- A headless runner cannot prove that Minecraft, shaders, audio devices, and
  launchers work together. Perform a final Prism/Forge launch check for material
  recording changes.
- Forge, MCP mappings, old Loom, and snapshot Mixin dependencies are fragile.
  Do not casually upgrade the wrapper or plugin graph as part of a release.

## Local packaging check

After building a versioned JAR, exercise the packaging helper without
publishing anything:

```powershell
node .github/release/package-release.mjs `
  --jar build/libs/recordish-1.0.0-forge-1.8.9.jar `
  --version 1.0.0 `
  --channel stable `
  --output-dir build/release-package `
  --repository ErDreiwen/recordish `
  --commit 0b05278d90d3568011258a9826484ba3abee5363
```

Inspect the generated JAR, checksum, and manifest together. Never upload only
one of them.
